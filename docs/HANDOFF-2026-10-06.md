## 3. Built, deployed, NOT verified

These shipped in the last session. Each fixed a real production bug, and none
has been confirmed by the test that matters.

### 4a — one auth source
`public/sm_auth.js`. `sm_current_user` in localStorage has no expiry; the
Supabase session does. Once it lapsed, the nav still said "signed in" while
every request went out with the anon key, failing only when a write hit RLS.
Now: one token source, refresh 120s ahead of expiry, one shared in-flight
refresh (Supabase rotates the refresh token on use, so parallel refreshes
invalidate each other), 401 retried once.

### 4b — likes (migration `012`)
`comment_likes` and `message_likes`, primary key on the pair, no downvotes.
Also widened `reports.target_id` and `events.ref_id` to `text`, because
`group_messages.id` is a **uuid** and `target_id` was `bigint` — so **the chat
Report button added in package 4 could never have worked**. Not yet confirmed
working.

### 4c — a week of news
Feed paginated by `published_at` cursor (not offset — the ingest job runs every
15 minutes, and arriving rows shift every offset and duplicate items across page
seams). 60 a page, 7-day window. Trending half-life 12h → 48h, Today / This week
toggle. Verified locally: pages 60 → 120 → 180 with every id unique across the
seams. Not verified on production.

### 4d — the silent-save regression
`SMAuth.endSession()` calls `signOut()`, and it had been wired into `apiSend`'s
401 path. A 401 is usually RLS refusing **one table** — so a single rejected
write, including fire-and-forget telemetry, tore down a working session. After
that the main club could not be saved and nothing logged as an error, because
everything about it was `console.warn`. Now `endSession()` fires only when a
refresh has actually failed, and every user-facing write failure raises a
visible toast.

### 4e — writes landing on the wrong account
**The most serious of the five.** `auth.html` redirected to `/` from an *async*
`getSession()` callback while the form was already usable. Submitting
credentials let the pending redirect navigate away mid-sign-in: the new session
never persisted, the old one survived in storage, and the app wrote as the
previous user while showing the new one's name. Confirmed on production — the
test account's club and follow changes all landed on `gomef23`, which held 10
follows while the test account had none.

Fixed by: removing the redirect in favour of an explicit "Already signed in as
X" banner; clearing any existing session before `signInWithPassword`; verifying
the stored session is the one just created; `scope:'local'` on both sign-out
paths (a failed global `signOut` can leave the local token in place); and
`resolveUser()` no longer patching the cached id to match the session — it
replaces the record, logs an error, and reloads.

Also in 4e: the club picker became one screen — main club above, also-following
below, one search filtering both.

## 4. The three open tests — run these first

All three need **two accounts**. None can be done from the SQL editor alone.

### 4.1 Which account is the page actually acting as?

In the browser console on `/`, signed in as each account in turn:

```js
await SMAuth.whoami()
```

It decodes the access token — the same bytes the server reads to compute
`auth.uid()` — and reports `jwtEmail`, `cachedEmail` and a `match` boolean.

- `match: true` → correct, the fix holds.
- `match: false` → the page is acting as `jwtEmail` while showing
  `cachedEmail`. **Every write lands on `jwtEmail`.** Sign out once with the
  current build and it will clear properly; if it recurs, 4e is not fixed.

Then the real test: sign in as the **test account**, change the main club and
add a follow, and check in SQL that they landed on the right row.

```sql
select u.email,
       p.main_club_id,
       t.name as main_club,
       (select count(*) from public.follows f where f.user_id = p.id) as follows
  from public.profiles p
  join auth.users u on u.id = p.id
  left join public.teams t on t.id = p.main_club_id
 order by u.email;
```

Expected: the change appears on the test account's row and **nothing** changed
on the other.

### 4.2 Does the chat Report button work?

This is what `012`'s `target_id` widening was for. As account B, open any club's
Community chat, report one of account A's messages, then:

```sql
select target_type, target_id, reason, status, created_at
  from public.reports
 where target_type = 'group_message'
 order by created_at desc
 limit 5;
```

Expected: a row whose `target_id` is a **uuid**. Before `012` this was
impossible — PostgREST rejected the uuid against a `bigint` column before any
policy saw it.

Then as the admin account, open Profile → the report queue. The card should read
**"abuse · message"**, quote the message, and offer **Delete message**.

### 4.3 Is the like bug a display bug or a security hole?

**Still genuinely open.** When B tapped 👍 on a comment A had liked, the count
went to 0 instead of 2. The client cause is fixed (identity now comes from the
JWT, and a DELETE that removes nothing reverts instead of painting as done). But
whether B could *actually* delete A's row was never settled: `comment_likes` was
empty when checked, which is inconclusive.

It cannot be tested from the SQL editor — **the SQL editor runs as the service
role and bypasses RLS entirely**, so a delete succeeding there proves nothing.

First, the fast check (`supabase/probe_like_policies.sql` section 1):

```sql
select tablename, policyname, cmd, roles, qual, with_check
  from pg_policies
 where schemaname = 'public'
   and tablename in ('comment_likes','message_likes')
 order by tablename, cmd;
```

Expected, three rows per table and **no UPDATE row**:

| cmd | expected |
|---|---|
| SELECT | `qual = true` |
| INSERT | `with_check = (auth.uid() = user_id)` |
| DELETE | `qual = (auth.uid() = user_id)` |

If the DELETE row's `qual` is `true`, or there is no DELETE policy while
`authenticated` holds the DELETE grant, stop and re-run `012`.

Then the definitive test, in the **browser console**, not the SQL editor.
Signed in as **A**, with a comment thread open — note the comment's id:

```js
await SMAuth.rest('comment_likes', {
  method: 'POST',
  headers: {'Content-Type':'application/json', Prefer:'return=representation'},
  body: JSON.stringify([{comment_id: COMMENT_ID, user_id: SMAuth.userId()}])
}).then(r => r.json())
```

Then signed in as **B**, in a different browser or a private window:

```js
await SMAuth.rest('comment_likes?comment_id=eq.COMMENT_ID', {
  method: 'DELETE',
  headers: {Prefer: 'return=representation'}
}).then(r => r.json())
```

There is deliberately **no `user_id` filter** on B's delete: this asks the
database to remove every like on that comment.

- Returns `[]` → the policy holds. Display bug only, already fixed.
- Returns A's row → **that is the hole.** Revoke immediately:

```sql
revoke delete on public.comment_likes from authenticated;
revoke delete on public.message_likes from authenticated;
```

Then confirm from the SQL editor whether A's row survived:

```sql
select * from public.comment_likes where comment_id = COMMENT_ID;
```

## 8. Things that will bite you

Collected from the last three sessions. Each one cost real time.

- **A reconstruction that production silently skips is still load-bearing.**
  `011` guessed `bigserial` for `groups` / `group_messages`; `create table if
  not exists` skipped it on production, so the guess did no damage *there* —
  but everything keyed to a message inherited the wrong type, and the chat
  Report button shipped broken.
- **PostgREST answers 204 for a DELETE or PATCH that matched nothing.** Both
  read as success. Use `Prefer: return=representation` wherever "did it actually
  happen" matters.
- **`reports.target_id` is polymorphic.** Comment 41 and group_message 41 are
  different rows — always key lookups on `target_type` **and** `target_id`.
- **A 401 is usually RLS refusing one table, not a dead session.** Never tear
  down a session over one.
- **`console.warn` is invisible** to anyone filtering the console to Errors. A
  failure the user needs to know about is `console.error` plus a toast.
- **Grid items default to `min-width: auto`.** A long club name refuses to
  shrink and scrolls the whole picker sideways at 375px.
- **Check layout at 375px by rendering it**, not by reading the CSS. Both
  picker bugs in 4e were invisible in the source.
